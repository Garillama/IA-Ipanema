# Delta aislado: alcance cerrado y supervisor del piloto

Autorizado preparar, NO integrar ni hacer HTTP a Rhino/Google. Solo tres módulos y dos tests. Se reutiliza el loop de crawl; no hay otro motor. Los cambios del modo general se limitan a condiciones opt-in y callback nulo. El watchdog vive dentro de engineering.py para la CLI, no modifica el orquestador de modelos.

--targets-manifest y --targets-sha256 son flags implementados en el CANDIDATO, aún ausentes del repositorio integrado. El manifiesto se lee una sola vez en el worker: máximo64KiB,hash exacto,JSON sin claves repetidas,proyecto/origen y cincoURLs literales únicas validadas por Policy. La CLI real se probó con --responses en un proyecto sintético; ningún GET salió a red.

Modo cerrado: queue inicial=five selected, sin home ni sitemaps. depthNone evita BFS;extrae/enlista enlaces observados pero nunca los solicita. Preserva extractor,classify,auditorías,transport y Robots. Global redirects máximo3 incluye robots y documentos;sin saltos externos/privados ni ciclos. Una respuesta ya observada en otra URL seleccionada no se vuelve a descargar ni se confunde con un ciclo;hay un test para esa reproducción. Cobertura del scope no afirma cobertura del sitio ni indexación.

Un solo Fetcher comparte presupuesto,rate y tiempos de robots/documentos. Caps:12GET,0.5/s,120s,20s por GET,2Mbody codificado y descomprimido,concurrencia1. Hasta8nodos=documentos5+3redirects. Restricciones de Robots pueden reducir aún más velocidad o bloquear. Los errores genéricos del transporte/Policy abortan el scope entero. DNS/TLS/gzip/headers seguros conservan la implementación revisada.

Checkpoint:callback opcional en Fetcher. Persiste atómicamente y hace fsync antes de que empiece cada transporte;si falla,no inicia esa petición. Los eventos completed y unconfirmed no afirman que un GET sin respuesta no llegó al servidor. planned contiene robots/targets y redirects conocidos;requests registra ordinal,URL y estados. No hay resume ni reintentos automáticos. Los errores conservan informe/checkpoint o la recepción de fallo del supervisor.

Supervisor POSIX en engineering.py: proceso fork con setsid, handshake ready validandoPGID y permiso go antes de trabajo. Dentro corren lectura/validación del manifiesto,checkpoint,HTTP,parsing y exportación. Pipe solo devuelve el resumen;ningún flag/env puede desactivar el watchdog. Al acercarse el techo de120s reserva hasta1s para TERM/KILL y reap;si el worker o descendiente ignoran TERM,el grupo recibeKILL. También limpia la sesión al completar o interrumpir la CLI. El padre restaura handlers;no quedan hijos ejecutando nuevas solicitudes. Si no confirma reap,devuelve stopped. La recepción de cancelación se escribe después de detener el trabajo;no continúa análisis ni HTTP durante esa escritura.

La función Python crawl sigue siendo un motor que recibe clock/transport para pruebas;el límite absoluto de proceso es propiedad de la entrada CLI supervisada propuesta,que será la única invocación de red solicitada para este piloto. No se autoriza usar una llamada Python directa para evitar esa supervisión.

Pruebas:209unitarias SEO(191base+18nuevas),13integraciones generales y9nuevas integraciones cortas;la prueba de120s se ejecutó por separado(no un resultado simulado). El caso120terminó en119.6s incluyendo la gracia;worker reaped,descendiente no activo,checkpoint conservado,noHTTP. El test120 y el módulo supervisor permanecen idénticos tras esa ejecución;se conserva binding. Las pruebas cortas congelan parsing/export y envíanSIGTERM al supervisor,verificando limpieza del grupo. Los descendientes no hicieron HTTP:se verificó que no quedan activos,por lo que no pueden seguir ejecutando solicitudes. Se documentan zombies no ejecutables si el reaper del sistema aún los conserva;no se confunden con procesos activos.

El parche se aplicó y revirtió en otro worktree de herramientas,verificando tres preimágenes y ausencia de dos altas. El repositorio integrado está intacto. Los artefactos de pruebas anteriores se conservan;se repitió la regresión SEO solo por modificar consumidores compartidos. No se reejecutó quick/TLS local sin necesidad.

Esta revisión pide decidir si el candidato es admisible para solicitar integración local exacta. No aprueba integrar ni red.
